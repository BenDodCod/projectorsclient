## Decisions Made

| Decision | Options Considered | Chosen | Rationale |
|----------|-------------------|--------|-----------|
| CONFIG_SECRET provisioning | Env var, CLI arg, file/registry | Env var `CONFIG_SECRET` | Matches note wording; natural for SCCM/MSI; no new secret channel in code |
| v2 key secret | `CONFIG_SECRET` vs dedicated `DEPLOYMENT_CONFIG_SECRET` | `CONFIG_SECRET` | Must match what web writes today; dedicated secret is a coordinated follow-up |
| Projector-password storage fix | Wire cred manager + plaintext, vs `set()` with pre-encrypted | `set()` with pre-encrypted | Wiring a cred manager risked regressing the `sql.password` path (`set()` auto-encrypts sensitive keys) |
| Commit flow | Direct to main vs branch + PR | Branch + PR (#1) | Crypto-touching change warrants review |

## Issues Encountered

### Issue 1: Projector password "double-handling" flag turned out cosmetic
- **Problem:** `apply_config_to_database` called `set_secure()` with an already-encrypted value, logging "Storing sensitive setting … without encryption".
- **Resolution:** That `SettingsManager` has no credential manager, so `set_secure()` passed through (no real double-encryption); nothing reads that settings key (UI uses the `projector_config` table). Switched to `set()` to match `sql.password` and remove the misleading warning.
- **Added to LESSONS_LEARNED:** Yes

### Issue 2: Decrypt not routed through a single chokepoint
- **Problem:** The plan assumed `_decrypt_credential` was the only decrypt site, but the projector password is also decrypted twice inside `apply_config_to_database`.
- **Resolution:** Added a `decrypt_deployment_credential()` dispatcher and used it at all three sites.
- **Added to LESSONS_LEARNED:** Yes
